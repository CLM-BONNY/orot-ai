# T08. 작동하는 데서 측정하고 개선하는 데로

이 트랙에서는 앞에서 배운 모델·검색·평가를 실제 웹 서비스에 연결한다. 지표를 외우는 대신 어떤 실패를 관찰하고 어떤 변경을 비교할지 설계한다.

<a id="ch29"></a>
## CH29. 웹 요청과 AI 백엔드

- 선수 학습: CH20, CH25, CH28
- 개념 ID: `http`, `api-contract`, `fastapi`, `asgi`, `mangum`, `serverless`, `async-io`, `background-job`
- 학습 목표: 요청 경로와 실행 환경의 역할을 설명하고 동기·비동기 설계를 선택한다.

<a id="ch29-p01"></a>
### CH29-P01. 버튼을 누른 뒤 어디에서 무엇을 할까

사용자가 React 화면에서 문제 생성 버튼을 누르면 브라우저는 API에 요청한다. 서버는 입력·자료·허용 범위를 확인하고 모델을 호출한 뒤 결과를 검증해 돌려준다. 화면에서 로딩을 보여주는 일과 서버에서 생성하는 일은 서로 다른 실행이다. 브라우저의 객관식 채점은 이 모델 호출과 별개로 처리할 수 있다.

HTTP 상태 코드는 전송과 API 처리 상태를 전달한다. 2xx라고 내용이 사실이라는 뜻은 아니다. 4xx·5xx·429·타임아웃을 구분하고, 문제 수·정답 형식 같은 서비스 결과도 별도 검증한다. 요청 ID를 응답과 로그에 공통으로 넣으면 한 요청을 추적하기 쉽다.

프런트에서 CORS 설정을 통과했다고 호출자가 인증된 것은 아니다. 인증은 누구인지, 인가는 무엇을 할 수 있는지 판단하는 일이다. 공개 API라면 브라우저 밖에서도 요청이 올 수 있다는 실행 조건을 고려해야 한다.

<a id="ch29-p02"></a>
### CH29-P02. FastAPI·Lambda·Mangum의 역할

FastAPI는 Python에서 HTTP API를 작성하는 웹 프레임워크다. Lambda는 이벤트가 발생하면 함수를 실행하는 환경이다. API Gateway가 넘긴 이벤트와 FastAPI가 기대하는 ASGI 요청 사이를 연결하는 어댑터로 Mangum을 사용할 수 있다. 변환 플러그에 비유할 수 있지만 실제 비즈니스 로직은 FastAPI와 그 내부 모듈에 있다.

일반 서버에서 ASGI 서버로 FastAPI를 실행한다면 이 Lambda 어댑터가 꼭 필요한 것은 아니다. 프레임워크, 실행 서버·환경, 이벤트 연결 도구를 구분하자. Docker 역시 모델이나 웹 프레임워크가 아니라 실행 환경을 패키징하는 수단이다.

서버리스는 서버가 없다는 뜻이 아니다. 인프라 관리의 상당 부분을 제공자가 맡지만 실행 시간·패키지·동시성·초기화·네트워크 제약은 남는다. 로컬에서 실행된 코드가 배포 환경에서도 같은 권한과 의존성을 갖는지 확인해야 한다.

<a id="ch29-p03"></a>
### CH29-P03. 기다림을 다루는 방법은 두 가지다

외부 모델 응답을 기다리는 것은 주로 I/O 대기다. async I/O는 기다리는 동안 다른 작업을 처리할 수 있도록 돕지만 모델 제공자의 생성 자체를 빠르게 하지는 않는다. CPU 계산을 event loop에서 오래 실행하면 다른 작업을 막을 수도 있다. 비동기 문법과 실제 병렬 실행은 같은 말이 아니다.

웹 요청 안에서 작업을 끝내는 동기 응답과, 작업 ID를 먼저 반환하고 나중에 결과를 조회하는 비동기 작업 구조도 구분한다. 후자는 큐·작업 상태·중복 처리·만료·실패 상태 관리가 필요하다. 단순히 함수에 `async`를 붙이는 것만으로 이 구조가 생기지 않는다.

첫 버전은 짧은 설명과 3문항 생성으로 시작할 수 있다. API Gateway HTTP API의 통합 한도는 최대 30초이므로 그보다 짧은 전체 마감 시간을 두고 실패를 처리한다. 더 긴 작업이 필요하면 큐와 작업 조회 방식 등을 비교한다. 제한값은 사용하는 서비스·API 종류의 공식 문서로 확인한다.

## CH30. 지연·비용·캐시

- 선수 학습: CH03, CH20, CH29
- 개념 ID: `latency`, `p95`, `cold-start`, `warm-invocation`, `cost-per-success`, `response-cache`, `cache-key`
- 학습 목표: 관측 구간을 구분하고 품질·표본 수를 포함해 속도와 비용을 비교한다.

<a id="ch30-p01"></a>
### CH30-P01. 어느 시간을 측정했는지 먼저 적기

브라우저 버튼 클릭부터 결과 표시까지에는 네트워크·서버·모델·화면 렌더링이 포함된다. 서버 처리 시간은 그 일부이고 모델 호출 시간은 다시 그 일부다. 각 구간의 시작과 끝을 정해야 숫자를 비교할 수 있다. 서버의 시간만 보고 사용자가 기다린 전체 시간이라고 쓰지 말자.

p50은 중앙값이고 p95는 측정 표본의 약 95%가 그 값 이하에 놓이는 분위수다. 상위 5%가 얼마나 오래 걸렸는지의 평균과 다르다. 구현마다 분위수 추정 방식이 다를 수 있고 표본이 적으면 불안정하므로 표본 수와 도구를 함께 적는다. 실패 요청을 제외하면 느린 요청이 타임아웃으로 빠져 p95가 좋아 보일 수 있어 실패율도 같이 본다.

Lambda의 콜드 시작에는 새 실행 환경의 초기화가 포함된다. 웜 호출은 이미 준비된 환경을 재사용하는 경우다. 첫 번째로 보낸 요청을 무조건 콜드라고 가정하지 않고 로그로 확인한다. 모델 호출이 대부분의 시간을 쓰면 Lambda 초기화 최적화의 전체 효과는 작을 수 있다.

<a id="ch30-p02"></a>
### CH30-P02. 싼 요청과 싼 성공은 다르다

모델 토큰·Lambda 실행·API 요청·로그 등을 포함해 비용 경계를 정한다. 모델의 입력·출력·캐시 토큰 요금이 다를 수 있고 단가는 서비스·시점·리전에 따라 달라진다. 실험일의 단가와 포함한 항목을 기록하자. 토큰 수만으로 모든 인프라 비용을 대신할 수는 없다.

전체 비용이 1,000원이고 요청이 100건이면 요청당 10원이다. 유효한 퀴즈 세트가 80개뿐이면 유효 결과당 12.5원이다. 이 숫자는 설명용 가상 예시다. 실패와 재시도 비용을 제외하면 실제 효율을 과장할 수 있다.

모델을 작게 바꾸거나 해설을 줄여 비용을 낮추더라도 품질 기준을 유지하는지 확인한다. “사용 가능한 결과 한 개를 얻는 비용”을 보면 싸지만 자주 틀리는 설정의 문제를 더 잘 발견할 수 있다. 시간·비용·품질을 함께 비교하자.

<a id="ch30-p03"></a>
### CH30-P03. 같은 답을 재사용해도 되는가

응답 캐시는 이미 만든 결과를 저장해 반복 요청에 재사용한다. 모델 내부 KV cache와 다르다. 캐시 키에는 자료·개념·모델·프롬프트 버전·언어·난이도처럼 결과에 영향을 주는 요소를 고려한다. 개인화 결과라면 사용자·권한 경계도 필요하다.

캐시된 퀴즈는 빠르지만 “새 문제” 버튼에서 매번 같은 문제가 나오면 기능 목적과 충돌한다. 기본 설명의 재사용과 새 복습 문제 생성을 구분해야 한다. 데이터 갱신 시 무효화와 TTL도 정한다. TTL만으로 원문 삭제나 권한 변경이 즉시 반영되는 것은 아니다.

캐시 도입 전후는 hit·miss를 분리하고 실제 예상 반복률에 맞춰 평가한다. 같은 입력만 반복해 거의 모두 hit인 결과를 새로운 질문의 성능처럼 제시하면 안 된다. 품질·개인화 의미를 유지하면서 계산을 줄이는지 판단하자.

## CH31. 동시성·과부하·재시도

- 선수 학습: CH26, CH29, CH30
- 개념 ID: `concurrency`, `throughput`, `rate-limit`, `backpressure`, `timeout`, `exponential-backoff`, `jitter`, `circuit-breaker`
- 학습 목표: 부하 수준과 처리 한계를 구분하고 재시도가 실패를 증폭하는 조건을 설명한다.

<a id="ch31-p01"></a>
### CH31-P01. 동시 사용자 수와 초당 요청 수는 다르다

10명이 응답을 받은 뒤 다음 요청을 보내는 테스트는 서버가 느려지면 새 요청 발생도 줄어든다. 반면 초당 일정 요청을 보내는 방식은 지연이 늘어도 외부 유입을 유지하려 한다. 둘은 서로 다른 부하 모델이다. VU 수만 보고 RPS가 같다고 생각하면 안 된다.

안정된 평균 상태와 일관된 관측 경계에서는 평균 동시 작업 수 L, 처리율 λ, 평균 체류 시간 W 사이에 `L=λW`라는 Little의 법칙을 적용할 수 있다. 초당 2건을 처리하고 평균 5초 머문다면 평균 동시 작업은 10건이다. 과부하로 대기열이 계속 커지는 구간에 같은 해석을 무비판적으로 적용하지 않는다.

동시 요청은 1→5→10→20처럼 단계적으로 높이며 실제 요청·완료 수, 처리량, 실패율, 지연을 기록한다. 테스트 발생기 자체가 병목인지도 확인한다. 관찰 범위에서 실패가 없었다면 그 범위를 기록하고 무한 처리 능력이라고 주장하지 않는다.

<a id="ch31-p02"></a>
### CH31-P02. 첫 실패는 어느 계층에서 나왔는가

429는 요청 제한의 신호일 수 있지만 외부 모델, API Gateway 등 어느 계층에서 나왔는지 확인해야 한다. Lambda 스로틀, 연결 오류, 생성 시간 초과, 검증 실패도 구분한다. 모든 오류를 “AI 오류”로 묶으면 개선 대상을 찾기 어렵다.

서버가 감당하지 못하는 요청을 무한히 받아 대기시키는 대신 처리 상한과 대기 제한을 두는 것이 backpressure의 한 방식이다. 빨리 실패를 알리는 fail-fast가 일부 상황에서 전체 지연과 자원 고갈을 줄일 수 있다. 그러나 거절률도 사용자 경험의 일부라서 함께 보고한다.

모델을 고정 응답이나 일정 지연으로 대체한 테스트는 서버 경로의 한계를 분리하는 데 도움이 된다. 실제 모델 테스트와 결과를 구분해야 한다. 실제 429를 보기 어렵다면 시험용 오류 주입으로 처리 로직을 검증하되 자연 발생 실패와 섞어 보고하지 않는다.

<a id="ch31-p03"></a>
### CH31-P03. 재시도는 공짜도 무조건 좋은 것도 아니다

한 번 실패한 요청을 다시 보내면 일시적 장애를 넘길 수 있다. 그러나 모두가 즉시 재시도하면 부하가 더 커진다. 지수 백오프는 대기 간격을 늘리고 jitter는 무작위 분산을 넣어 요청이 한꺼번에 몰리는 것을 완화한다. 재시도 횟수·전체 마감 시간·대상 오류를 제한해야 한다.

400 같은 잘못된 입력은 같은 요청을 반복해도 낫지 않을 수 있다. 여러 계층이 각각 재시도하면 호출 수가 곱으로 늘 수 있다. 사용자 요청 한 건과 실제 모델 호출 횟수를 따로 기록하자. 재시도 과정에서 저장 같은 부작용이 중복되지 않게 멱등성도 고려한다.

클라이언트가 기다리다 연결을 끊어도 서버나 외부 모델 작업이 반드시 즉시 취소되는 것은 아니다. 취소 전파와 과금 여부는 실제 동작을 확인해야 한다. Circuit breaker는 반복 장애 동안 호출을 잠시 제한하는 접근이지만 복구 판단과 운영 복잡성이 생긴다. 확인한 병목에 맞춰 필요한 대응부터 적용한다.

<a id="ch32"></a>
## CH32. 관측·버전·지속적인 품질 관리

- 선수 학습: CH11, CH24, CH27, CH30, CH31
- 개념 ID: `observability`, `metrics-logs-traces`, `slo`, `data-drift`, `concept-drift`, `rollback`, `canary`, `experiment-report`
- 학습 목표: 운영 신호와 품질을 연결하고 재현 가능한 최종 실험을 설계한다.

<a id="ch32-p01"></a>
### CH32-P01. 숫자·사건·경로를 함께 관찰하기

메트릭은 요청 수·지연·오류율 같은 수치 추세를 보여준다. 로그는 특정 요청의 사건과 상태를, trace는 여러 구성 요소를 지난 경로와 구간 시간을 연결한다. 전부 같은 내용을 반복 저장하는 것이 아니라 서로 다른 질문에 답하도록 구성한다.

지연, 트래픽, 오류, 포화도는 서비스의 기본 신호다. AI 서비스에서는 유효 출력률·근거 정확성·토큰·재시도도 필요하다. 서버가 살아 있어도 퀴즈 정답이 틀리면 학습 기능은 실패한 것이다. 인프라 상태와 제품 품질을 함께 관찰한다.

SLO는 서비스가 달성하려는 측정 가능한 목표다. “빠르게” 대신 어떤 요청 집단·기간·성공 조건·시간 기준인지 정의한다. 실제 측정 전 임의의 숫자를 약속하기보다 기준선과 사용자 필요를 보고 정하고, 오류 예산의 의미도 그 목표와 연결한다.

<a id="ch32-p02"></a>
### CH32-P02. 시간이 지나면 입력과 정답 관계가 달라진다

Data drift는 입력 분포 변화, concept drift는 입력과 목표의 관계 변화라는 구분으로 이해할 수 있다. 초보자 중심 서비스에 전문가가 들어오면 질문 분포가 달라질 수 있고, 교육 과정 변경으로 같은 질문의 기대 답이 바뀔 수도 있다. 드리프트 신호가 곧 품질 하락의 확정 증거는 아니므로 실제 결과를 확인한다.

모델 별칭, 프롬프트, 검색 인덱스, 학습 글, 정답표, 라이브러리 중 무엇이 바뀌었는지 추적한다. 모델명 하나만 적으면 재현에 부족할 수 있다. 평가 결과와 배포 버전을 연결하고 잘못된 변경은 되돌릴 수 있게 한다.

작은 사용자 집단에 먼저 적용하는 canary 배포나 제한된 비교를 사용할 수 있다. 다만 실험 집단의 차이와 표본 수를 고려해야 한다. 답변 점수가 좋았다는 이유로 메모 저장이나 접근성 같은 일반 기능의 회귀를 놓치지 않도록 핵심 흐름도 확인한다.

<a id="ch32-p03"></a>
### CH32-P03. 이 사이트의 최종 실험 설계

고정 자료를 짧음·중간·김으로 나누고, 개념 정의·비교·계산·상황 판단 질문을 준비하자. 자료·문제 수·모델·프롬프트 버전을 고정해 기준선을 저장한다. 콜드·웜 지연, 모델 호출 시간, 토큰, 유효 결과율, 품질 검토를 함께 기록한다.

개선은 한 변수씩 비교한다. 예를 들어 관련 페이지만 제공해 시간과 비용이 줄었다면 누락된 개념이나 예외로 품질이 떨어지지 않았는지 본다. 모델을 바꿨다면 같은 루브릭으로 검토하고, 캐시를 썼다면 hit·miss를 나누며, 재시도를 넣었다면 같은 부하에서 추가 호출 수와 대기시간을 본다.

최종 보고서에는 문제, 기준선, 변경, 조건, 표본 수, 결과, 한계, 다음 판단을 적는다. 개선이 없었던 실험도 기록한다. “어떤 설정이 언제나 최고다”가 아니라 “우리 자료와 부하에서 이 선택이 이 효과와 대가를 보였다”라고 말할 수 있으면 목표를 달성한 것이다.
