# T04. NLP와 Transformer

문자열에서 토큰·표현·관계·출력으로 이어지는 길을 따라간다. “모델이 중요한 단어를 본다”는 설명에서 멈추지 않고, 무엇을 어떻게 계산하는지 살펴본다.

<a id="ch13"></a>
## CH13. 토큰화와 언어 입력

- 선수 학습: CH02, CH09
- 개념 ID: `tokenization`, `subword`, `bpe`, `vocabulary`, `special-token`, `padding`, `truncation`
- 학습 목표: 토큰·문자·단어를 구분하고 입력 길이와 특수 토큰을 관리한다.

<a id="ch13-p01"></a>
### CH13-P01. 컴퓨터가 읽는 단위는 단어와 다르다

“딥러닝을 공부합니다”를 사람이 두 덩어리로 읽더라도 토크나이저는 여러 조각으로 나눌 수 있다. 토큰은 모델이 처리하는 기호 단위이며, 단어·문자·공백·바이트 조각 등에 대응할 수 있다. 정확한 분할은 토크나이저마다 다르므로 예시 분할을 일반 규칙으로 외우지 말자.

토큰 ID는 어휘표 안의 번호다. ID 200이 ID 100보다 두 배 강한 의미를 갖는 것은 아니다. 모델은 이 번호로 임베딩 테이블의 행을 찾아 실수 벡터를 얻는다. 같은 숫자라도 다른 토크나이저에서는 다른 기호를 뜻할 수 있다.

책을 읽기 전에 인쇄된 문자를 일정한 부품으로 분해하는 비유를 생각할 수 있다. 부품의 종류가 많으면 어휘표가 커지고, 너무 잘게 나누면 시퀀스가 길어진다. 토큰화는 사소한 전처리가 아니라 문맥 길이·비용·표현 가능성에 영향을 주는 설계다.

<a id="ch13-p02"></a>
### CH13-P02. Subword와 특수 토큰

Subword 토큰화는 자주 쓰는 조각을 활용하면서 낯선 단어도 작은 조각으로 표현하려 한다. BPE는 빈번한 기호 쌍을 합치는 방식의 대표 예다. 실제 적용은 초기 기호·바이트 사용·정규화·특수 토큰 처리에 따라 달라진다. 모든 토크나이저가 BPE인 것도 아니다.

시작·종료·패딩·역할 구분 같은 특수 토큰은 일반 단어와 다른 기능을 갖는다. 대화 모델은 사용자·도우미 메시지를 정해진 대화 형식으로 받아 학습되기도 한다. 역할 라벨을 단순 텍스트로 흉내 내는 것과 모델이 기대하는 chat template을 쓰는 것은 다를 수 있다.

한글은 항상 한 글자당 한 토큰이라는 식으로 비용을 계산하면 틀릴 수 있다. 실제 모델의 토크나이저로 길이를 확인하는 편이 정확하다. 언어·기호·코드에 따라 같은 문자 수도 토큰 수가 달라진다.

<a id="ch13-p03"></a>
### CH13-P03. Padding과 truncation은 의미를 바꿀 수 있다

길이가 다른 문장을 한 배치로 묶을 때 padding으로 길이를 맞출 수 있다. 이때 패딩 위치가 실제 내용처럼 계산되지 않도록 attention mask 등을 사용한다. 패딩 마스크와 생성 모델의 미래 토큰 차단 마스크는 목적이 다르다.

문맥 한도를 넘으면 truncation으로 일부를 버릴 수 있다. 하지만 마지막에 있는 정답 조건이나 질문이 잘리면 모델의 문제가 아니라 입력 구성의 문제가 된다. “처음 N토큰”을 기계적으로 선택하기보다 남겨야 할 지시·질문·근거를 우선순위로 관리해야 한다.

우리 사이트에서 긴 글과 최근 대화를 함께 보내면 글 길이뿐 아니라 시스템 지시와 대화 형식도 입력 예산을 쓴다. 출력에 사용할 여유도 고려해야 한다. 토큰 한도는 지식이 저장되는 용량과 같지 않고, 한 요청에서 처리할 수 있는 범위에 가깝다.

<a id="ch14"></a>
## CH14. 희소 표현과 학습된 임베딩

- 선수 학습: CH02, CH13
- 개념 ID: `bag-of-words`, `tf-idf`, `embedding`, `contextual-embedding`, `sentence-embedding`, `bi-encoder`
- 학습 목표: 텍스트 표현의 선택이 검색 결과에 미치는 영향을 설명한다.

<a id="ch14-p01"></a>
### CH14-P01. 단어의 출현을 세는 방법

Bag-of-Words는 문서를 단어 출현 수 등으로 표현한다. 어휘표가 크면 대부분의 값이 0인 희소 벡터가 된다. “모델이 캐시를 사용한다”와 “캐시가 모델을 사용한다”는 같은 단어를 포함해도 순서와 역할이 다르지만 단순 출현 표현에서는 구분이 어려울 수 있다.

TF-IDF는 문서 안에서 자주 나오되 전체 문서 어디에나 나오지는 않는 단어를 강조하는 방식이다. 학습 글 전체에 “설명”이 많이 등장하면 구분력이 낮을 수 있고, 특정 페이지의 “역전파”는 그 페이지를 찾는 단서가 될 수 있다. 정확한 식과 평활화는 구현에 따라 달라진다.

이 방식은 낡았다는 이유만으로 버릴 것이 아니다. 제품 코드, 오류 번호, 고유명사의 정확한 일치가 중요한 검색에서는 강한 기준선이 된다. 다만 같은 뜻의 다른 표현을 연결하려면 추가 장치가 필요하다.

<a id="ch14-p02"></a>
### CH14-P02. 임베딩은 학습된 좌표다

임베딩은 단어나 문장 등을 실수 벡터로 표현한 것이다. 학습 목표가 관련 표현을 가까이 놓도록 설계되면 의미 검색에 쓸 수 있다. 도서관에서 제목이 달라도 비슷한 주제의 책을 근처에 놓는 비유다. 좌표가 학습되었다는 점이 사람이 만든 분류표와 다르다.

정적 단어 임베딩은 같은 단어에 같은 벡터를 주는 반면 문맥적 표현은 주변 내용에 따라 달라질 수 있다. “은행에서 돈을 찾다”와 “은행 열매를 줍다”를 생각하면 차이가 보인다. 하지만 문맥적이라고 항상 단어 뜻을 정확히 구분한다는 보장은 없다.

토큰 표현을 평균했다고 언제나 좋은 문장 검색 벡터가 되는 것도 아니다. 문장 간 비교에 맞춰 학습된 모델과 pooling 방식이 중요하다. 생성에 좋은 모델이 검색 임베딩에도 최선이라고 가정하지 말자.

<a id="ch14-p03"></a>
### CH14-P03. 검색 임베딩을 선택하는 기준

Bi-encoder는 질문과 문서를 각각 벡터로 만든 뒤 비교한다. 문서 벡터를 미리 계산할 수 있어 빠른 검색에 유리하다. 대신 질문과 문서를 처음부터 함께 읽는 모델보다 세밀한 일치 판단에 제약이 있을 수 있다. 후자의 방식은 reranker에서 다시 다룬다.

임베딩 모델을 평가할 때는 한국어, 도메인, 문서 길이, 질문 형태가 실제 서비스와 비슷해야 한다. “모델 정확도”라는 검색어가 “평가 지표” 페이지를 찾는지, “API-429”가 정확한 오류 문서를 찾는지 확인하자. 전체 평균뿐 아니라 유형별 실패를 읽는다.

같은 모델·같은 전처리·같은 버전으로 만든 벡터를 비교해야 한다. 모델을 바꿨는데 예전 문서 벡터를 그대로 두면 좌표계가 섞인다. 재색인과 검색 인덱스 버전 관리는 임베딩 도입의 일부다.

<a id="ch15"></a>
## CH15. Attention의 Q·K·V

- 선수 학습: CH02, CH09, CH14
- 개념 ID: `attention`, `query-key-value`, `scaled-dot-product`, `self-attention`, `multi-head-attention`
- 학습 목표: Attention을 가중합으로 계산하고 사람의 주의·설명 가능성과 구분한다.

<a id="ch15-p01"></a>
### CH15-P01. 누구의 정보를 얼마나 가져올까

Attention은 현재 위치가 다른 위치들의 정보를 얼마나 섞을지 계산하는 방식이다. “민수는 책을 샀고 그것을 읽었다”에서 “그것”을 표현할 때 “책”과 관련된 정보를 활용할 수 있다. 단순히 중요한 단어에 형광펜을 칠하는 것보다, 각 위치의 표현을 다른 위치의 정보로 갱신하는 계산에 가깝다.

Query는 무엇과 맞출지, Key는 맞춤 점수를 계산할 대상, Value는 실제로 섞어 가져올 정보라고 생각할 수 있다. 이들은 보통 입력 표현에 서로 다른 학습된 선형 변환을 적용해 만든다. 사람이 적은 검색어와 색인 문서 그 자체가 Q·K·V라는 뜻은 아니다.

도서관 질문 카드·책의 분류표·책 내용이라는 비유가 도움은 되지만, 실제로는 모두 벡터와 행렬이다. 모델이 Q라는 이름의 의식적 질문을 만드는 것은 아니다. 비유는 계산 역할을 구분하는 데까지만 사용하자.

<a id="ch15-p02"></a>
### CH15-P02. 점수에서 가중합으로

대표적인 scaled dot-product Attention은 다음과 같다.

$$\operatorname{Attention}(Q,K,V)=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}+M\right)V$$

마스크 M은 접근을 막을 위치에 매우 작은 값 또는 음의 무한대를 더해 softmax 확률이 0에 가깝게 되게 한다. 점수를 0으로 바꾸는 것만으로는 차단되지 않는다. softmax에서 `exp(0)=1`이기 때문이다.

두 Value가 `[10,0]`, `[0,10]`이고 가중치가 `[0.8,0.2]`라면 결과는 `[8,2]`다. 가중치는 두 정보가 얼마나 섞이는지 정한다. 점수 나눗셈은 차원 증가에 따라 내적 크기가 커지는 현상을 완화하려는 장치다.

길이가 n인 시퀀스의 기본 full self-attention 점수 행렬은 n×n이다. 이 구조가 긴 입력의 계산·메모리 부담과 연결된다. 실제 구현은 최적화될 수 있으므로 공식 하나만으로 모든 배포 지연을 정확히 예측할 수는 없다.

한 head에서 Q와 K가 각각 `[n,d_k]`, V가 `[n,d_v]`라면 QKᵀ는 `[n,n]`, 최종 가중합은 `[n,d_v]`다. 문장 길이만큼 후보 위치를 비교한 뒤 각 위치의 새 표현을 만든 셈이다. 이 모양을 직접 적어보면 유사도 점수와 전달할 정보가 다른 행렬이라는 점이 분명해진다.

<a id="ch15-p03"></a>
### CH15-P03. 여러 관점을 섞되 설명과 동일시하지 않기

Multi-head Attention은 여러 학습된 투영으로 관계를 계산하고 결과를 결합한다. 한 번의 비교보다 다양한 관계를 표현할 여지가 생긴다. 그러나 첫 head는 문법, 둘째는 대명사처럼 역할이 항상 명확하게 나뉘는 것은 아니다.

Self-attention은 Q·K·V가 같은 시퀀스에서 나오고, cross-attention은 질문 역할과 참조 정보가 서로 다른 시퀀스에서 나오는 형태를 말한다. 번역 decoder가 encoder 출력을 참고하는 경우가 대표적인 cross-attention 예다.

높은 attention weight가 곧 “이 단어 때문에 답했다”는 완전한 인과 설명은 아니다. 여러 head·층·잔차 경로와 후속 변환이 출력을 만든다. Attention 시각화는 유용한 관찰 도구지만 사실 검증이나 해석의 최종 근거로만 사용하지 않는다.

### 확인 문제

<a id="ch15-q01"></a>
#### CH15-Q01 · 계산

Value `[10,0]`, `[0,10]`에 가중치 `[0.8,0.2]`를 적용한 가중합은?

<a id="ch16"></a>
## CH16. Transformer와 언어 모델 구조

- 선수 학습: CH10, CH13, CH15
- 개념 ID: `transformer`, `encoder`, `decoder`, `causal-mask`, `positional-encoding`, `residual-connection`, `feed-forward-network`
- 학습 목표: encoder·decoder의 접근 범위와 학습·생성의 병렬성 차이를 설명한다.

<a id="ch16-p01"></a>
### CH16-P01. Attention만으로 순서를 모두 알 수 있을까

Transformer 블록에는 Attention뿐 아니라 위치별 feed-forward 변환, 잔차 연결, 정규화 등이 들어간다. Attention은 위치 사이 정보를 섞고, feed-forward 부분은 각 위치의 표현을 비선형으로 변환한다. 잔차 연결은 기존 표현을 더해 정보와 기울기가 전달될 경로를 만든다.

Self-attention은 순서 정보를 별도로 주지 않으면 위치 순서를 구분하는 데 제약이 있다. 위치 임베딩, 사인·코사인 방식, 회전 위치 표현 같은 장치로 순서나 상대 위치 정보를 반영한다. 모든 Transformer가 같은 위치 표현을 쓰는 것은 아니다.

단어 카드의 내용만 놓고 관계를 계산하는 사람에게 카드의 위치 표시를 추가하는 비유를 쓸 수 있다. 하지만 위치 표시가 있다고 문맥 길이를 무한히 늘려도 잘 작동하는 것은 아니다. 학습된 길이·방법·구현 제약을 함께 본다.

<a id="ch16-p02"></a>
### CH16-P02. Encoder·decoder·encoder-decoder

Encoder 중심 모델은 보통 입력 양쪽 문맥을 참고해 표현을 만든다. BERT 계열의 masked language modeling은 일부 가린 토큰을 복원하는 대표적인 학습 방식이다. 이 표현은 분류나 토큰 분석 등에 활용할 수 있다.

Decoder 중심의 causal 언어 모델은 현재 위치에서 미래 토큰을 보지 못하도록 마스킹하고 다음 토큰을 예측한다. GPT 계열이 대표적인 예다. Encoder-decoder 모델은 입력을 읽는 부분과 출력을 생성하는 부분을 연결하며 번역·요약 등에 사용할 수 있다. 구조 이름과 모든 학습 목표가 일대일로 고정되는 것은 아니므로 실제 모델 설명을 확인한다.

우리 도우미가 앞의 대화를 바탕으로 다음 답변을 쓰는 과정은 일반적으로 causal 생성과 연결된다. 반면 검색용 문장 표현은 생성용 출력과 목적이 다르다. 같은 Transformer라는 이름만으로 모델을 서로 대체할 수는 없다.

<a id="ch16-p03"></a>
### CH16-P03. 학습은 병렬이어도 생성은 순차일 수 있다

Causal 학습에서는 정답 토큰 시퀀스를 이미 알고 있다. 입력을 한 칸 이동해 각 위치의 다음 토큰을 정답으로 두고, 마스크로 미래 정답을 못 보게 하면서 여러 위치의 손실을 병렬로 계산할 수 있다. 정답을 미리 넣되 접근 범위를 제한하는 점이 핵심이다.

자기회귀 생성에서는 아직 다음 토큰을 모른다. 하나를 고르고 그 토큰을 이어 붙여 다음 분포를 계산한다. 따라서 학습의 위치별 병렬성과 출력 생성의 순차성을 같은 것으로 보면 안 된다. 뒤에서 배울 KV cache는 이미 계산한 정보를 재사용해 이 과정을 돕는다.

연습으로 “나는 오늘” 다음 토큰을 생성하는 순간과 “나는 오늘 공부한다” 전체로 학습하는 순간을 구분해보자. 학습 때는 미래 문장이 데이터로 있지만 causal mask가 접근을 막는다. 생성 때는 미래 문장 자체가 아직 없다. 이 차이가 모델의 동작과 지연을 이해하는 열쇠다.

#### CH16-Q02 · 성능 이해
