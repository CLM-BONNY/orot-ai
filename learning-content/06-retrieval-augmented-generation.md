# T06. 근거를 찾아 답하는 시스템

RAG를 벡터 DB 하나로 기억하지 않고 수집·검색·선택·생성·검증의 흐름으로 배운다. 사이트의 작은 학습 자료에서 시작해 문서 규모가 커지는 상황으로 확장한다.

<a id="ch21"></a>
## CH21. RAG의 전체 흐름과 도입 판단

- 선수 학습: CH14, CH18, CH20
- 개념 ID: `rag`, `ingestion`, `retrieval`, `grounding`, `indexing`, `query-pipeline`
- 학습 목표: 색인 준비와 질의 처리를 구분하고 검색이 필요한 상황을 설명한다.

<a id="ch21-p01"></a>
### CH21-P01. 자료를 찾아놓고 답변에 쓰게 하기

학습자가 “재현율과 정밀도가 어떻게 달라?”라고 묻는다. 시스템은 평가 지표 페이지를 찾아 관련 구간을 도우미에게 전달하고 설명하게 할 수 있다. 모델 파라미터를 바꾸지 않고 외부 지식을 요청 문맥에 공급하는 RAG의 기본 아이디어다.

오픈북 시험에 비유할 수 있다. 필요한 페이지를 찾는 능력과 찾은 페이지를 읽어 답하는 능력은 다르다. 엉뚱한 책을 펼쳤거나 올바른 문장을 잘못 읽으면 답도 틀릴 수 있다. RAG가 환각을 완전히 제거한다는 주장은 이 두 단계를 생략한 것이다.

검색 방법은 키워드·SQL·ID 조회·벡터 검색 등 다양할 수 있다. RAG를 구현하려면 반드시 거대한 벡터 DB부터 설치해야 하는 것은 아니다. 이미 현재 페이지를 아는 사이트에서는 ID 기반 자료 조회가 더 직접적일 수 있다.

<a id="ch21-p02"></a>
### CH21-P02. 오프라인 준비와 온라인 처리를 나누기

준비 단계에서는 문서를 수집하고, 파싱·정제하고, 검색 단위로 나누고, 메타데이터와 표현을 만들어 색인한다. 온라인 단계에서는 질문을 받아 권한 조건과 함께 검색하고, 후보를 선택해 문맥을 구성하고, 답변과 출처를 생성한다.

PDF의 표가 줄글로 깨지거나 제목이 본문과 분리되면 검색 전에 이미 정보가 손상된다. 수식·코드·표·각주의 구조를 보존하는 것이 중요하다. 생성 모델의 크기를 늘려도 파싱 중 사라진 근거는 돌아오지 않는다.

답변에 사용한 문서 버전과 구간 ID를 남기자. 원문이 바뀌었을 때 과거 답변이 어느 규정을 참조했는지 확인할 수 있다. “검색 결과가 있다”보다 “이 질문에 필요한 근거가 현재 버전으로 들어왔다”가 더 구체적인 성공 조건이다.

<a id="ch21-p03"></a>
### CH21-P03. 우리 사이트에서는 어디까지 필요할까

현재 페이지의 개념을 묻는 질문이라면 해당 페이지와 연결 개념을 서버에서 조회해 넣으면 된다. 전체 목차를 가로질러 “정규화와 확률 보정은 어떻게 달라?”라고 묻는다면 여러 자료를 찾아야 한다. 질의 범위가 검색 설계를 결정한다.

처음부터 복잡한 질의 재작성·다중 검색을 넣으면 비용과 디버깅 지점이 늘어난다. 작은 평가 질문 목록으로 단순 ID 조회나 키워드 검색을 먼저 측정하고, 실제로 놓치는 유형이 무엇인지 본 뒤 확장하자.

도입 판단을 문장으로 적어보자. “새로운 문서를 출처와 함께 사용해야 하므로 검색을 도입한다”는 요구와 연결된다. “다들 벡터 DB를 쓰므로 도입한다”는 기술 선택만 있다. 운영할 구성 요소마다 해결할 실패를 설명할 수 있어야 한다.

<a id="ch22"></a>
## CH22. 청킹·메타데이터·문서 갱신

- 선수 학습: CH13, CH21
- 개념 ID: `chunking`, `overlap`, `parent-child-retrieval`, `metadata`, `document-version`, `index-update`
- 학습 목표: 검색 단위와 답변 문맥 단위를 구분하고 갱신·삭제를 설계한다.

<a id="ch22-p01"></a>
### CH22-P01. 글을 자르는 위치가 답변을 바꾼다

긴 문서 전체를 하나의 검색 벡터로 만들면 여러 주제가 섞일 수 있다. 너무 작은 조각은 제목·주어·예외 조건을 잃기 쉽다. 청킹은 단순히 길이를 줄이는 것이 아니라 검색하고 전달할 의미 단위를 정하는 작업이다.

“유료 플랜은 30일 보관한다. 단, 시험 계정은 7일이다”를 서로 다른 조각으로 분리하면 잘못된 일반화가 생길 수 있다. 제목과 본문, 표의 열 이름과 값, 코드와 설명을 함께 보존해야 한다. 페이지와 챕터가 이미 의미 있게 나뉜 우리 사이트는 그 구조를 첫 청크 경계로 활용할 수 있다.

일정 토큰 수, 문장·문단, 제목 계층, 의미 변화 등 여러 기준을 비교할 수 있다. 최적 청크 길이가 모든 문서에 동일한 상수로 존재하지는 않는다. 토크나이저와 질문 유형도 결과를 바꾼다.

<a id="ch22-p02"></a>
### CH22-P02. 겹침과 부모 문맥의 절충

인접 청크 일부를 겹치게 하면 경계에서 정보가 잘리는 문제를 완화할 수 있다. 대신 중복 저장·중복 검색·입력 토큰 증가가 생긴다. overlap을 크게 만들수록 무조건 좋아지는 것은 아니다. 같은 근거의 복제본이 상위 결과를 채울 수도 있다.

작은 청크로 정확히 찾고 그 청크가 속한 더 큰 문단이나 페이지를 생성 문맥으로 제공하는 parent-child 방식도 있다. 검색 단위와 생성 단위를 분리하는 것이다. 작은 책갈피로 위치를 찾은 뒤 관련 절 전체를 읽는 비유다.

확장한 문맥이 너무 길면 지연과 혼란이 늘 수 있다. top-k, 중복 제거, 문맥 길이 예산을 함께 조절한다. 단순한 검색 점수 향상만 보고 실제 답변 품질 검사를 생략하면 안 된다.

<a id="ch22-p03"></a>
### CH22-P03. 문서는 바뀌고 삭제된다

각 청크에는 문서·페이지·개념 ID, 제목, 버전, 갱신 시각, 출처 위치, 접근 권한 같은 메타데이터를 붙일 수 있다. 사용자 필터와 권한 조건은 검색과 문맥 구성에 실제로 적용해야 한다. 메타데이터에 적었다고 자동으로 보호되는 것은 아니다.

원문을 수정하면 관련 청크와 임베딩도 갱신해야 한다. 새 버전을 추가하고 예전 청크를 남겨두면 서로 모순된 답이 나올 수 있다. 삭제한 자료가 색인·캐시·복제본에 남지 않도록 삭제 경로도 생각한다.

임베딩 모델을 바꾸면 재임베딩과 재색인을 계획한다. 콘텐츠 버전, 임베딩 모델 버전, 인덱스 버전은 다른 축이다. 새 색인을 준비하고 평가한 뒤 전환하면 중간 상태를 사용자에게 노출할 위험을 줄일 수 있다.

<a id="ch23"></a>
## CH23. 검색·하이브리드·재정렬

- 선수 학습: CH02, CH14, CH22
- 개념 ID: `bm25`, `dense-retrieval`, `ann`, `hnsw`, `hybrid-search`, `rrf`, `reranker`, `cross-encoder`
- 학습 목표: 후보 검색과 재정렬을 구분하고 검색 방식의 장단점을 비교한다.

<a id="ch23-p01"></a>
### CH23-P01. 정확한 단어와 비슷한 의미를 함께 보기

BM25 같은 키워드 검색은 단어 일치, 문서 내 빈도, 문서 길이 등을 이용해 관련성을 계산한다. Dense 검색은 학습된 벡터의 거리·내적을 사용한다. 오류 코드·이름에는 키워드가 유리할 수 있고, 표현이 다른 같은 의미에는 dense 검색이 도움이 될 수 있다.

벡터가 많아지면 모든 벡터와 정확히 비교하는 비용이 커질 수 있다. ANN은 일부 정확성을 절충해 빠르게 가까운 후보를 찾는 접근이다. HNSW는 그래프 기반 대표 방법이다. 빠르게 찾았다는 것과 실제 필요한 근거를 찾았다는 것은 별개다.

거리 설정도 중요하다. 정규화한 벡터의 내적과 코사인 유사도는 연결되지만, 정규화 없이 임의로 대체하면 순위가 바뀔 수 있다. 사용 라이브러리가 제곱 L2를 반환하는지 등 점수 정의도 확인한다. 서로 다른 점수의 숫자 크기를 그대로 비교하지 말자.

<a id="ch23-p02"></a>
### CH23-P02. 하이브리드는 점수 합치기부터 주의하기

키워드와 dense 검색 결과를 결합하면 서로 놓치는 후보를 보완할 수 있다. 다만 BM25 점수 12와 코사인 점수 0.8을 그대로 더하면 척도가 맞지 않는다. 점수 정규화나 순위 기반 결합 같은 방법을 사용하고 실제 평가로 확인한다.

RRF는 결과별 순위 r에 대해 대략 `1/(k+r)` 형태의 값을 더해 결합한다. 여기의 k는 순위 기여를 완화하는 상수이며, 검색 결과 개수 top-k와 같은 뜻이 아니다. 순위 기반이라는 점이 서로 다른 점수 척도를 직접 더하는 문제를 피하도록 돕는다.

하이브리드가 모든 질문에 자동으로 더 좋지는 않다. 후보 수·중복 제거·필터·가중치가 영향을 준다. 고유명사, 동의어, 부정 표현 등 유형별 평가 질문을 준비해 어떤 실패가 줄었는지 확인하자.

<a id="ch23-p03"></a>
### CH23-P03. 많이 찾고 정밀하게 다시 읽기

빠른 검색으로 후보 20개를 찾은 뒤 reranker로 상위 5개를 고를 수 있다. Cross-encoder는 질문과 문서를 함께 읽어 관련성을 계산하는 대표 방식이다. 미리 문서 벡터만 만들어두는 bi-encoder보다 후보별 계산이 무거울 수 있으므로 전체 문서에 바로 적용하기보다 좁힌 후보에 사용한다.

Reranker는 후보에 없는 문서를 되살릴 수 없다. 필요한 근거가 처음 20개에 없으면 재정렬만으로 해결되지 않는다. 반대로 후보에 근거가 있는데 상위 문맥에 못 들어오면 재정렬과 문맥 선택을 조사할 이유가 있다.

마지막 문맥에서는 중복을 줄이고 질문에 필요한 정의·예외·근거를 함께 제공한다. 후보 검색의 top-k, 재정렬 후 개수, 최종 토큰 예산을 구분해 기록하자. 이 세 수를 모두 “검색 개수”라고 부르면 실험을 재현하기 어렵다.

A. 버튼 색상
B. 최종 답변의 글자 크기
C. 재정렬만 반복하면 반드시 해결된다.
D. 색인·전처리·질의·필터·후보 검색 단계

**정답: D.** Reranker는 존재하는 후보를 재배치한다. 후보 누락은 앞 단계에서 조사한다. 관련 페이지: CH23-P03.

**인출 연습 CH23-R01:** Bi-encoder 검색과 cross-encoder 재정렬을 계산 방식과 적용 범위로 비교하라.

<a id="ch24"></a>
## CH24. RAG 평가와 권한

- 선수 학습: CH08, CH21, CH23
- 개념 ID: `recall-at-k`, `mrr`, `groundedness`, `answer-correctness`, `citation`, `abstention`, `retrieval-acl`
- 학습 목표: 검색·근거 사용·정답·권한을 별도로 평가하고 실패를 분류한다.

<a id="ch24-p01"></a>
### CH24-P01. 검색기는 검색 문제로 평가한다

질문마다 관련 문서를 표시한 평가 자료를 만들면 Recall@k를 측정할 수 있다. 관련 문서가 두 개이고 상위 5개에 그중 하나가 있으면 이 질문의 Recall@5는 1/2다. “관련 문서 하나라도 찾은 질문의 비율”인 hit rate와 같은 정의가 아니다. 관련성 표시가 불완전하면 점수도 왜곡될 수 있다.

MRR은 첫 관련 결과 순위의 역수를 평균한다. 첫 근거가 2위이면 그 질문의 값은 1/2다. 여러 근거를 모두 찾는지와 첫 근거를 빨리 찾는지는 다른 질문이다. nDCG처럼 관련성의 등급과 순위를 고려하는 지표도 있다.

작은 사이트에서는 수동으로 표시한 수십 개 질문으로 시작할 수 있다. 정답 페이지, 필요한 문장, 관련 개념, 답할 수 없는 질문을 함께 적자. 평가 세트의 일부를 설정 선택에 사용하고, 최종 점검용은 따로 두면 반복 튜닝의 과적합을 줄일 수 있다.

<a id="ch24-p02"></a>
### CH24-P02. 근거를 잘 따랐는데 답이 틀릴 수도 있다

Groundedness 또는 faithfulness는 답의 주장이 제공 문맥에 의해 뒷받침되는지 보는 관점이다. Answer correctness는 정답 자체가 맞는지를 본다. 오래된 문서를 충실히 따라 틀린 답을 만들 수 있고, 자료에는 없는 내용을 우연히 맞힐 수도 있다. 두 지표를 합쳐 생각하면 원인을 놓친다.

출처 검사는 링크 존재 여부보다 구체적이어야 한다. 인용한 구간이 실제 해당 주장을 뒷받침하는가, 예외를 빠뜨리지 않았는가, 다른 문서의 숫자를 옮기지 않았는가를 본다. 자료에 없을 때 답변을 보류하는 능력도 평가한다.

실패를 “근거 미검색”, “근거 순위 낮음”, “문맥 선택 중 누락”, “근거 해석 오류”, “원문 오류”로 나누면 다음 조치가 보인다. 평가용 모델을 쓰더라도 일부 사례를 사람이 검토해 판정 기준이 실제 목표와 맞는지 확인한다.

<a id="ch24-p03"></a>
### CH24-P03. 잘 찾는 것보다 먼저 읽을 권한이 있는가

여러 사용자의 개인 노트를 검색하는 서비스라면 사용자 A의 질문에 B의 노트가 들어가면 안 된다. 서버가 확인한 사용자·조직 권한을 검색 조건에 적용하고, 생성 모델에 넘기기 전에도 허용 자료인지 확인해야 한다. 모델에게 “다른 사용자 자료는 말하지 마”라고 적는 것만으로 보호할 수 없다.

검색 후 화면에서만 숨기면 늦다. 이미 모델 입력과 로그에 들어갔을 수 있다. 공유 캐시도 사용자·권한·문서 버전을 고려해야 한다. 같은 질문이라는 이유로 타인의 개인 답변을 재사용하면 정보가 섞일 수 있다.

현재 설계의 개인 노트는 브라우저에 저장하므로 서버가 전체 노트를 자동으로 알고 있다고 가정하지 않는다. 향후 노트 동기화·검색을 추가할 때는 동의한 전송 범위와 권한 검증을 함께 설계한다. 공개 학습자료 검색과 개인 자료 검색은 데이터 경계가 다르다.

### 확인 문제

<a id="ch24-q01"></a>
#### CH24-Q01 · 지표 계산

관련 문서가 2개이고 상위 5개 결과에 그중 1개가 있다. 이 질문의 Recall@5는?

A. 0.5
B. 0.2
C. 1.0
D. 5.0

**정답: A.** 관련 문서 전체 중 찾은 비율인 `1/2`다. `1/5`는 다른 정의이며 recall의 분모가 아니다. 관련 페이지: CH24-P01.

<a id="ch24-q02"></a>
#### CH24-Q02 · 보안 경계

개인 노트 검색 권한을 적용할 가장 적절한 위치는?

A. 답변이 생성된 뒤 CSS로 숨기기
B. 모델에게 주의하라고만 지시하기
C. 서버가 확인한 권한으로 검색·문맥 전달·캐시 접근을 제한하기
D. 질문을 익명 문자열로 바꾸기만 하기

**정답: C.** 허용되지 않은 자료를 모델에 넘기지 않는 데이터 경계가 필요하다. 관련 페이지: CH24-P03.
