# T05. LLM을 이해하고 선택하기

큰 언어 모델이 어떻게 만들어지고 어떤 계산으로 답을 이어 쓰는지 배운다. 특정 제품의 최신 이름이나 순위 대신 모델을 비교하고 한계를 판단할 기준을 다룬다.

<a id="ch17"></a>
## CH17. 사전학습과 다음 토큰 예측

- 선수 학습: CH06, CH13, CH16
- 개념 ID: `pretraining`, `self-supervised-learning`, `causal-language-modeling`, `cross-entropy-lm`, `parameters`, `moe`
- 학습 목표: 자기지도학습의 정답 생성 방식과 다음 토큰 학습의 가능성·한계를 설명한다.

<a id="ch17-p01"></a>
### CH17-P01. 정답은 문장 안에서 만든다

“오늘은 비가 온다”라는 글을 토큰으로 바꾸면 앞 토큰들로 다음 토큰을 예측하는 학습 예제를 만들 수 있다. 사람이 각 위치마다 정답표를 새로 작성하지 않아도 원문에 다음 토큰이 있기 때문이다. 이를 자기지도학습의 한 방식으로 볼 수 있다. “정답이 없다”가 아니라 데이터 자체에서 학습 목표를 만든다는 뜻이다.

Causal 언어 모델은 앞 문맥이 주어졌을 때 다음 토큰의 조건부 분포를 학습한다. 여러 위치의 음의 로그확률을 합하거나 평균해 손실을 구성한다. 토큰 길이·마스크·평균 방식에 따라 손실 비교 조건이 달라질 수 있다.

다음 토큰 예측은 단순해 보이지만 다양한 문맥을 예측하려면 문법·사실·코드 구조·문체 등의 패턴이 유용하다. 그렇다고 모든 지식을 정확한 사실 테이블로 저장하는 것은 아니다. 그럴듯한 이어 쓰기와 검증된 사실 응답 사이에는 간극이 남는다.

<a id="ch17-p02"></a>
### CH17-P02. 데이터와 규모가 만드는 능력과 한계

사전학습은 많은 자료에서 범용적인 표현과 패턴을 학습하는 단계다. 데이터의 양뿐 아니라 중복, 품질, 언어 비율, 저작권·사용 조건, 개인정보 처리도 중요하다. 잘못된 자료가 많으면 모델이 그 패턴을 학습할 수 있다. 학습 손실이 낮다는 사실만으로 모든 응용 품질을 평가할 수 없다.

파라미터 수는 모델의 학습 가능한 값의 규모를 나타내지만 곧바로 지식량이나 서비스 품질을 의미하지 않는다. 데이터·구조·학습 연산량·후속 학습이 함께 영향을 준다. 토큰 수와 파라미터 수를 혼동하지 말자. 전자는 데이터나 처리 길이, 후자는 모델 내부 값의 개수다.

MoE는 여러 expert 중 일부를 선택해 계산하는 구조다. 총 파라미터 수와 토큰당 활성 파라미터 수가 다를 수 있다. 계산이 줄어도 가중치 저장과 통신·라우팅 비용이 남으므로 “총 크기만큼 항상 계산한다”와 “메모리도 같은 비율로 줄어든다”는 주장 모두 조심해야 한다.

<a id="ch17-p03"></a>
### CH17-P03. 기반 모델을 곧바로 도우미로 볼 수 없는 이유

기반 언어 모델은 문장을 이어 쓰는 데 학습되었을 수 있다. 사용자의 요구에 맞게 답하고 도구를 쓰는 대화 도우미의 행동은 후속 학습과 실행 환경의 영향을 받는다. 모델과 서비스 전체를 같은 물건으로 보면 검색·도구·정책이 어디서 작동하는지 알기 어렵다.

모델에 오늘 바뀐 규정을 물어봤을 때 정확한 답이 나온다고, 그 규정을 방금 학습한 것은 아닐 수 있다. 서비스가 검색해 전달했을 수도 있고 우연히 맞췄을 수도 있다. 모델의 사전학습 지식, 요청에 넣은 문맥, 외부 도구 결과를 구분하자.

우리 사이트의 기본 문제는 사람이 검토한 콘텐츠로 두고 새 복습 문제만 생성하면 출처와 역할이 명확해진다. 생성 결과를 학습 콘텐츠의 확정 사실처럼 자동 편입하지 않고 검증하는 절차도 필요하다.

## CH18. 지시 학습·선호 학습·모델 적응

- 선수 학습: CH10, CH17
- 개념 ID: `sft`, `rlhf`, `dpo`, `fine-tuning`, `peft`, `lora`, `quantization`, `distillation`
- 학습 목표: 지식 공급·행동 조정·메모리 최적화를 서로 다른 문제로 구분한다.

<a id="ch18-p01"></a>
### CH18-P01. 대답하는 방식을 학습시키기

SFT는 입력과 바람직한 응답 예제로 모델을 지도 학습시키는 방식이다. “이 개념을 비유로 설명해줘”에 원하는 설명을 짝지어 줄 수 있다. 새로운 문서 내용을 전달하는 것과 설명 방식·출력 형식을 학습하는 것은 목적이 다르다. 파인튜닝을 했다고 최신 사실이 계속 자동 갱신되지는 않는다.

선호 학습은 같은 입력에 대한 여러 응답 중 무엇을 더 선호하는지 활용한다. 대표적인 RLHF 파이프라인은 선호 자료로 보상 모델을 만들고 강화학습을 활용한다. DPO는 선호 쌍으로 정책을 직접 최적화하는 접근이다. 모든 정렬 방식이 같은 구현이나 보장을 갖는 것은 아니다.

선호된 답이 사실상 정답이라는 보장은 없다. 사용자가 자신감 있는 답을 좋아하면 사실성보다 말투를 보상할 위험도 있다. 데이터 수집 기준과 평가가 중요하다. 좋은 태도로 말하는 것과 근거가 맞는 것을 별도 항목으로 보자.

<a id="ch18-p02"></a>
### CH18-P02. LoRA는 작은 수정 공간을 학습한다

전체 파인튜닝은 많은 가중치를 갱신한다. LoRA는 기반 가중치를 고정하고 일부 행렬의 변화량을 낮은 rank의 행렬 곱으로 표현하는 대표적인 PEFT 방법이다. 대략 `W'=W+BA`로 생각할 수 있다. 큰 설계도 전체를 다시 그리는 대신 수정 지침을 덧붙이는 비유다.

학습 파라미터와 optimizer 상태를 줄일 수 있지만 기반 모델을 실행하는 메모리와 연산이 사라지지는 않는다. 어떤 층을 대상으로 하는지, rank와 데이터가 어떤지에 따라 품질이 달라진다. “작은 adapter이므로 언제나 원래 능력을 그대로 보존한다”는 뜻도 아니다.

RAG는 요청 때 근거를 제공하고, 파인튜닝은 모델의 파라미터를 바꾼다. 둘은 결합할 수 있다. 자주 바뀌는 지식을 근거와 함께 답해야 한다면 검색을 먼저 검토하고, 반복적인 행동·형식 문제가 있으면 예제·프롬프트·학습을 비교하는 식으로 목적을 나누자.

<a id="ch18-p03"></a>
### CH18-P03. 양자화와 증류는 다른 축이다

양자화는 가중치나 활성값 등을 더 낮은 정밀도로 표현해 메모리나 계산 비용을 줄이려는 방법이다. 단순한 가중치 저장만 계산하면 70억 개 값을 2바이트로 저장할 때 약 140억 바이트가 필요하다. 실제 실행에는 KV cache·활성값·메타데이터·프레임워크 여유가 추가되므로 이 숫자가 필요한 전체 GPU 메모리는 아니다.

낮은 정밀도가 항상 더 빠른 것도 아니다. 하드웨어와 커널 지원, 변환 비용, 메모리 접근의 병목에 따라 달라진다. 정확도 변화도 실제 과제에서 평가해야 한다. LoRA는 학습할 변화량의 구조, 양자화는 수치 표현 방식이므로 서로 결합할 수 있다.

증류는 큰 모델이나 다른 감독 신호를 이용해 작은 모델을 학습시키는 접근이다. 교사의 오류도 전달될 수 있고 학습 목표와 데이터가 결과를 좌우한다. 세 기술을 모두 “모델 압축”이라고만 기억하지 말고 무엇을 바꾸는지 구분하자.

<a id="ch19"></a>
## CH19. Logits·샘플링·생성 설정

- 선수 학습: CH03, CH09, CH16
- 개념 ID: `softmax`, `temperature`, `greedy-decoding`, `top-k`, `top-p`, `stop-condition`, `structured-generation`
- 학습 목표: 생성 설정이 분포와 길이에 미치는 영향을 이해하고 사실성 보장과 구분한다.

<a id="ch19-p01"></a>
### CH19-P01. 다음 토큰의 후보에서 하나를 고르기

모델은 문맥에서 다음 토큰의 logits를 계산한다. softmax로 분포를 만든 뒤 가장 높은 후보를 고르거나 분포에서 샘플링할 수 있다. Greedy decoding은 매 단계 가장 높은 점수를 고르는 방식이다. 한 단계의 최선이 전체 문장에 대한 전역 최적이나 사실 정답을 보장하지는 않는다.

Temperature T는 보통 logits를 T로 나눈 뒤 분포를 계산하는 방식으로 작동한다. 양수 T가 낮으면 상대적으로 높은 점수에 더 집중하고, 높으면 분포가 더 평평해진다. T=0은 수식에 그대로 대입할 수 없으며, API나 구현이 별도 greedy 동작 등으로 처리할 수 있다.

낮은 temperature는 변동을 줄이는 데 도움이 될 수 있지만 사실 오류를 치료하는 약이 아니다. 확률이 높게 학습된 잘못된 패턴을 더 일관되게 출력할 수도 있다. 백엔드 비결정성이나 모델 버전 변화도 있으므로 0 설정을 완전한 재현성 보증으로 보지 않는다.

<a id="ch19-p02"></a>
### CH19-P02. 후보를 몇 개까지 남길까

Top-k는 상위 k개 후보를 남기고 다시 확률을 정규화해 샘플링한다. Top-p는 높은 확률부터 누적해 기준 p에 도달하는 후보 집합을 사용한다. 전자는 개수를, 후자는 누적 확률 질량을 기준으로 삼는다. temperature와의 적용 순서와 지원 조합은 구현을 확인한다.

확률이 `[0.6,0.25,0.1,0.05]`일 때 p=0.8의 전형적인 nucleus 선택은 앞 두 후보를 남긴다. 합이 0.85로 기준을 넘기기 때문이다. 정답이 그 밖에 있으면 후보 제한이 오히려 정답을 배제할 수도 있다. 창의성·다양성·정확성을 하나의 손잡이로 완전히 조절할 수는 없다.

퀴즈는 같은 문장을 반복하지 않는 다양성도 필요하지만 정답 정확성이 더 중요하다. 난이도·문제 유형·중복 검사를 명시하고 결과를 평가해야 한다. 단순히 temperature를 올리는 것으로 교육 품질을 정의하지 말자.

<a id="ch19-p03"></a>
### CH19-P03. 길이 제한과 올바른 완료

출력 토큰 상한은 비용과 최악의 생성 길이를 제한하는 도구다. 너무 작으면 JSON 중간이나 해설 중간에서 끊길 수 있다. HTTP 200이 왔어도 문제가 완성되었는지, 종료 이유가 길이 한도인지 확인해야 한다.

정지 토큰·stop 문자열·구조화 출력 등은 구현에 따라 지원 방식이 다르다. JSON 문법이 맞는 것, 정해진 필드가 있는 것, 정답이 맞는 것은 세 단계다. 형식을 제한한다고 근거 없는 설명이 사라지지는 않는다.

생성 설정을 바꾸는 실험에서는 문제 수와 해설 길이도 함께 고정하자. 새 설정에서 더 짧은 문제를 만들었다면 속도 향상의 일부가 단순 출력 감소일 수 있다. 품질·토큰·시간을 함께 기록해야 비교를 해석할 수 있다.

<a id="ch20"></a>
## CH20. 문맥·환각·추론 메모리

- 선수 학습: CH13, CH16, CH19
- 개념 ID: `context-window`, `hallucination`, `conversation-state`, `prefill`, `decode`, `kv-cache`, `ttft`
- 학습 목표: 문맥과 장기 기억을 구분하고 생성 지연과 환각의 원인을 분석한다.

<a id="ch20-p01"></a>
### CH20-P01. 문맥은 펼쳐놓은 참고 자료다

모델 요청에 현재 페이지·질문·최근 대화를 넣는 것은 책상 위에 참고 자료를 펼쳐놓는 것과 비슷하다. 파라미터를 갱신하는 학습과 다르다. 대화가 이어지는 것처럼 보이더라도 서비스가 이전 메시지나 상태를 관리해 전달하는 경우가 많다. 장기 기억은 별도의 저장·선택·조회 설계가 필요하다.

문맥 한도는 자료가 그 안에 들어간다는 뜻이지, 모든 부분을 똑같이 잘 활용한다는 보장이 아니다. 관련 없는 글을 많이 넣으면 중요한 조건을 놓치거나 비용과 지연이 늘 수 있다. 요약으로 줄일 때도 중요한 예외나 숫자가 사라질 수 있다.

우리 도우미는 현재 페이지와 직접 연결된 개념 자료를 우선 넣고 대화 길이를 제한하는 방식으로 시작할 수 있다. 어떤 자료와 버전을 답변에 사용했는지 기록하면 나중에 잘못된 답의 원인을 조사하기 쉽다.

<a id="ch20-p02"></a>
### CH20-P02. 환각은 말투로 판별할 수 없다

생성형 AI가 근거 없는 사실이나 잘못된 출처를 그럴듯하게 만드는 현상을 흔히 환각이라고 부른다. 학습 자료의 한계, 모호한 질문, 잘못된 검색 결과, 근거 사용 실패 등 여러 원인이 있다. 외부 지식을 못 찾았는데 자신 있게 이어 쓰는 경우도 있다.

대응은 한 가지가 아니다. 근거가 필요한 질문에는 자료를 제공하고, 자료에 없으면 모른다고 답하게 하며, 숫자 계산은 도구로 확인하고, 출력 근거를 검증한다. 하지만 RAG나 좋은 지시도 정확성을 완전히 보장하지 않는다. 출처 URL이 존재하는 것과 그 출처가 해당 주장을 뒷받침하는 것도 다르다.

교육 서비스에서는 잘못된 설명이 학습자의 기억에 남을 수 있다. 기본 자료와 정답을 검토하고 생성 결과의 오류 신고·수정 경로를 두자. “답변이 길고 자신 있다”는 품질 기준 대신 주장 단위의 정확성과 근거를 본다.

<a id="ch20-p03"></a>
### CH20-P03. 입력을 읽는 시간과 이어 쓰는 시간

추론을 단순화하면 입력 문맥을 처리하는 prefill과 다음 토큰을 이어 만드는 decode로 나눌 수 있다. 첫 토큰까지 시간인 TTFT와 전체 완료 시간은 다르다. 스트리밍은 처음 내용을 더 빨리 보여줄 수 있지만 전체 작업의 계산량을 자동으로 줄이지는 않는다.

KV cache는 이전 토큰의 key·value를 재사용해 생성 중 반복 계산을 줄이는 장치다. 문맥과 동시 요청이 늘면 캐시 메모리도 커질 수 있다. 이는 완성된 답변을 저장했다가 돌려주는 응답 캐시와 다른 개념이다.

외부 API를 쓰면 제공자 내부의 모든 시간을 직접 볼 수는 없다. 서버에서 관찰한 모델 호출 시간, 첫 출력 시간, 전체 시간을 구분해 기록하고 관측 범위를 명시한다. 문맥을 줄일지 출력을 줄일지는 실제 병목을 보고 결정해야 한다.
